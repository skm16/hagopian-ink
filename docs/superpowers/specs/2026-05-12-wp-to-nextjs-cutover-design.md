# WP → Next.js Cutover (hagopianink.com) — Design Spec

**Date:** 2026-05-12
**Author:** Sean (with Claude)
**Target cutover:** 2026-05-13 (Wednesday)
**Status:** Approved design, implementation plan to follow

---

## 1. Goal

Replace the current live WordPress site at `hagopianink.com` with a Next.js 15 (App Router) application hosted on Vercel. WordPress remains the CMS, accessible at `cms.hagopianink.com` (subdomain on the existing WP Engine install), and feeds the Next.js site via the `jab` / `wp-headless-kit` MCP-adapter SDK.

**Non-goals (deferred to a later phase):**
- Hand-tuned per-page meta copy on the static marketing pages (use sensible defaults from current site's copy; refine in code later)
- Animated/branded OG images via `@vercel/og` (use static OG image)
- Custom 404 page polish beyond Next.js defaults
- Migration of remaining `case-studies.ts` hardcoded data into WP
- Performance audit and Core Web Vitals tuning beyond Next.js/Vercel defaults
- Reconciling case studies that exist only in `case-studies.ts` and not in the WP `works` CPT (the URL list shows ~17 works in WP; `case-studies.ts` has 24 — implementer to verify and document the delta as a follow-up ticket, not block cutover)

## 3. Rendering & data fetching

**Pattern:** Server components by default. Each page is an `async function` that calls jab SDK directly and renders HTML.

```ts
// app/work/[slug]/page.tsx
import { jabClient } from '@/lib/jab/client';
import { getWorksBySlug } from '@/lib/sdk';

export default async function CaseStudyPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const { works } = await getWorksBySlug(jabClient, { slug });
  const work = works[0];
  if (!work) notFound();
  return <CaseStudy work={work} />;
}
```

**Concurrency rule:** Per the jab gotchas memory, `client.ts` `ensureInitialized()` is not concurrency-safe — never `Promise.all` two SDK calls on a fresh client. All SDK calls in a single request are sequential `await`s. The api-server's `works.ts` route already follows this pattern; copy it.

**Caching strategy:** All fetches are tagged for on-demand revalidation.

```ts
// inside the SDK call wrapper or via jab client config
fetch(url, {
  method: 'POST',
  body: ...,
  next: { tags: [`work-${slug}`, 'works'] },
});
```

Default revalidate behavior: pages cache indefinitely, invalidated only by webhook. No time-based ISR — the webhook is the source of truth.

**Client components:** Only the interactive pieces get `'use client'`:
- Mobile-pages slider auto-advance (DOM measurement, intersection observer)
- Desktop-pages carousel
- Contact form (form state, validation)
- Nav (mobile menu toggle, scroll-driven state)
- Any framer-motion `motion` element that uses `useInView`

### 4.3 Metadata fallback chain

`lib/seo/resolve-metadata.ts` exposes `resolveMetadata(post)` that returns `{ title, description, ogImage }` from this priority order:

1. `post.yoast_head_json.title` / `.description` / `.og_image` (when authored in WP Yoast UI)
2. ACF tagline / hero (for `works`: `header_subtitle` or first text block; for posts: `journal_short_desc`)
3. WP-generated `excerpt` (stripped of HTML)
4. Site default

The site default per route type:
- Works: `"<work title> — Case Study | Hagopian Ink"`, description `"How Hagopian Ink helped <client> achieve <outcome from tagline>"`, OG `home_screenshot.jpg`

- Static pages: hand-authored in each `page.tsx`

### 4.4 JSON-LD strategy

**Don't pass through Yoast's frontend output.** Emit our own clean graph from React components:

- `<OrganizationSchema />` in root layout (sitewide, hardcoded values from table 4.1)
- `<WebSiteSchema />` in root layout with `SearchAction` pointing to `/?s={search_term_string}` (matches current — preserves site age signal)
- `<WebPageSchema />` + `<BreadcrumbSchema />` per page via a helper reading route + metadata
- `<ArticleSchema />` only on case studies and blog posts

Yoast remains installed on WP for the admin UX (client keeps using the familiar SEO sidebar when editing posts). We just don't render Yoast's frontend HTML.

### 4.5 Sitemap & robots

**`app/sitemap.ts`:**
- Static routes hard-coded (12 entries: /, /about, /contact, /work, /blog, /expertise + 6 sub, /privacy-policy, /terms-of-use)
- Dynamic: fetch all `works` slugs from WP via `getOurWork` (max 100), fetch all post slugs via `getPosts` (max 100), emit one entry each
- `changefreq` + `priority` per route type (homepage daily/1.0, case studies monthly/0.8, blog weekly/0.6, static monthly/0.5)
- Sitemap revalidated by the same webhook that revalidates content (tag: `sitemap`)

**`app/robots.ts`:**
- Allow all, point to sitemap
- Disallow `/api/*`
- Preview deployments get `x-robots-tag: noindex` automatically via middleware checking `NEXT_PUBLIC_VERCEL_ENV !== 'production'`

### 4.6 Image SEO

- `next/image` everywhere — automatic responsive srcsets, lazy loading, WebP/AVIF
- `alt` text from WP ACF `alt` field where present; fall back to post title
- `next.config.ts` `images.remotePatterns`:
  - `cms.hagopianink.com` (primary, post-cutover)
  - `hagopianink.wpengine.com` (interim, until cms DNS active)
  - `hagopianink.wpenginepowered.com` (legacy, for any URLs still pointing here)

### 4.7 Fonts

The four custom fonts (Playfair Display, Fira Sans, Sackers Gothic Std, Paulo Goode Didonesque) get migrated from WP-served URLs to `next/font/local` — self-hosted, preloaded, and not render-blocking. Font files copied to `public/fonts/`.

### 4.8 Submitting to Google

- Domain ownership verified in Google Search Console (DNS TXT record at GoDaddy or Vercel meta tag)
- Submit `https://hagopianink.com/sitemap.xml` on day-1 of cutover
- GSC URL Inspection → "Request indexing" on top 10 pages immediately after cutover

  - ACF
- Existing theme `skmframework` stays — still renders WP-side previews of edits

### 5.3 jab / wp-headless-kit production readiness

**Critical:** the `wp-headless-kit` plugin has 5 patches that currently live only on the LocalWP install. Without them on production, `/work` silently breaks. These must be applied before cutover:

1. `Schema.php` `flexible_content_variants()`: replace `'const' => $name` with `'enum' => [$name]`
2. `PostTypeListAbility.php` `batch_terms()`: add `'fields' => 'all_with_object_id'` to the `wp_get_object_terms` call
3. `PostTypeListAbility::shape_row()`: accept a `$taxonomies` arg and initialize each taxonomy slot to `[]` before filling, so posts with no terms in a public taxonomy don't fail output schema validation
4. `PostTypeListAbility::pick_variant()`: accept either `'const' => X` (legacy) or `'enum' => [X]` (current schema), so the runtime variant pick aligns with patch #1
5. (5th from gotchas memory) the additional post-with-no-terms validation guard inside `shape_row()`'s output-schema construction

**Application path:** Fork `wp-headless-kit` into `wordpress/plugins/wp-headless-kit-patched/` in this repo, apply the patches, and deploy via WP Engine Git Push so the patches survive any upstream plugin update.

**Re-sync the SDK against production:** After plugin install + patches, run `jab sync c:\Projects\New-Ink-Site` against `https://hagopianink.wpengine.com`. Commit the regenerated `lib/sdk/*` and updated `.jab/manifest.json` + `.jab/config.json`. Typecheck and fix any drift.

**Production WP credentials:**
- Create dedicated API user (e.g., `headless-api`) with Editor role
- Generate Application Password
- Store in Vercel env vars only; do NOT commit to `.env.example`
- The dev `.env.local` credentials (skm / ykKV-…) stay pointed at LocalWP

### 5.4 Webhook revalidation

**WP side (WP Webhooks plugin):**
- Trigger: `post_save`, `post_delete` for `works` and `post` post types
- Action: POST to `https://hagopianink.com/api/revalidate`
- Body: `{ secret: "<REVALIDATE_SECRET>", tag: "<post_type>", slug: "<slug>" }`

**Next.js side (`app/api/revalidate/route.ts`):**
- Validate `secret` matches `process.env.REVALIDATE_SECRET`
- Call `revalidateTag(body.tag)` and `revalidateTag(\`${body.tag.slice(0,-1)}-${body.slug}\`)` (e.g. `works` + `work-pepsi-email-marketing`)
- Also revalidate `sitemap` tag so new posts appear in the sitemap immediately
- Return `{ revalidated: true, now: Date.now() }`
- Log to Vercel logs for observability

**Secret:** 32-char random string, stored in Vercel env `REVALIDATE_SECRET` and WP Webhooks plugin config.

## 6. DNS & cutover plan

### 6.1 Current DNS state

- Registrar: GoDaddy
- Nameservers: `ns5.secureserver.net`, `ns6.secureserver.net` (GoDaddy-managed)
- Apex `A` record: currently points at WP Engine IP

### 6.2 DNS changes at GoDaddy

**Add before cutover (no traffic impact):**
- `cms.hagopianink.com` CNAME → WP Engine CNAME target (provided by WP Engine User Portal when alternate domain is added)
- `_vercel` TXT record → Vercel-provided value (proves domain ownership to Vercel)
- (optional) Google Search Console verification TXT record

**Change at cutover:**
- Apex `A` record: WP Engine IP → `76.76.21.21` (Vercel)
- `www` CNAME: WP Engine → `cname.vercel-dns.com`

**TTL discipline:**
- Lower apex TTL to 300s at least 1 hour before cutover (note: we accept some users may sit on stale DNS until the OLD TTL window expires — typically 1hr at GoDaddy)
- After 48hr of stability, raise apex TTL back to 3600s

### 6.3 Cutover sequence (Wednesday 2026-05-13)

Sequence assumes Vercel preview deploy is already green and redirects tested.

**T-2hr (Wednesday morning):**
- GoDaddy: lower apex TTL to 300s
- Vercel: final preview deploy from `main`, manual smoke test on preview URL
- Vercel: verify all env vars set, secret matches WP Webhooks config

**T-0 (cutover):**
- GoDaddy: change apex `A` → `76.76.21.21`
- GoDaddy: change `www` CNAME → `cname.vercel-dns.com`
- Watch Vercel logs for first traffic + any 404 surge
- Verify `hagopianink.com` loads from Vercel within ~5 min

**T+15min:**
- Submit `https://hagopianink.com/sitemap.xml` to Google Search Console
- GSC URL Inspection → request indexing for `/`, `/work`, `/about`, top 5 case studies
- Verify Bing Webmaster Tools doesn't throw a verification error (msvalidate.01 tag is in HTML)

**T+1hr:**
- Curl-test 10 random redirect entries from the URL list to confirm 308s land on the right destination
- Check Vercel logs for 404 patterns; add redirect entries for any legitimate hits

**T+24hr:**
- Review GSC for crawl errors
- Re-test webhook revalidation: edit a post in WP admin, verify page updates within ~5 sec
- Check 404 logs again

**T+48hr:**
- Raise apex DNS TTL to 3600s
- Decision point: keep `hagopianink.wpenginepowered.com` accessible (default) or redirect to apex

**T+7d:**
- Compare GSC impressions/clicks to baseline
- Any pages with significant ranking drop → investigate (missed redirect, thin content, mismatched meta)

### 6.4 Rollback

If something goes critically wrong post-cutover (site down >5 min, 50%+ traffic drop, broken content):
- GoDaddy: revert apex `A` → original WP Engine IP, `www` CNAME → original WP Engine target
- With TTL at 300s, traffic returns to old WP site within ~5 min
- Vercel deploy stays as-is; fix forward and re-cut over

## 7. Redirects

Implemented in `next.config.ts` `redirects()` (returns `Promise<Redirect[]>` so it can be generated programmatically).

### 7.1 Blog post redirects (~66 entries)

Pattern: `https://hagopianink.com/<slug>/` → `/blog/<slug>`. Entries are explicit (no regex) because root-level slugs could collide with reserved paths.

**Implementer step:** read `HagopianInk_WP_Urls.md` at build time (or paste the list into a `redirects.json` generated from it) and emit one `{ source: '/<slug>', destination: '/blog/<slug>', permanent: true }` per blog row. Examples:
- `/7-luxury-jewelry-websites-we-love-2/` → `/blog/7-luxury-jewelry-websites-we-love-2`
- `/tedx-navesink/` → `/blog/tedx-navesink`
- `/celebrating-20-years-at-hagopian-ink/` → `/blog/celebrating-20-years-at-hagopian-ink`

Each entry: `{ source, destination, permanent: true }` (308).

### 7.2 Case study redirects (~17 entries)

Pattern: `https://hagopianink.com/works/<slug>/` → `/work/<slug>` (note: WP uses plural `works`, new app uses singular `work`). Implementable as a single wildcard:

```ts
{ source: '/works/:slug', destination: '/work/:slug', permanent: true }
```

This single rule covers all 17 entries plus any future works. Verified examples:
- `/works/pepsi-email-marketing/` → `/work/pepsi-email-marketing`
- `/works/sesame-street-mobile-email/` → `/work/sesame-street-mobile-email`
- `/works/award-winning-logos/` → `/work/award-winning-logos`

### 7.3 Taxonomy archive redirects

- `/work/design-branding/` → `/work`
- `/work/email/` → `/work`
- `/work/ux-design/` → `/work`

### 7.4 Static-page redirects

- `/case-studies/` → `/work`
- `/blog/` → `/blog` (Next.js handles trailing-slash normalization automatically; explicit for clarity)
- `/contact/` → `/contact`
- `/expertise/` → `/expertise`
- `/mobile-email-checklist/` → `/contact`
- `/thank-you-for-joining/` → `/`
- `/sign-up-for-our-newsletter/` → `/contact`
- `/wbe-branding-agency/` → `/about`
- `/print/` → `/work`

### 7.5 Privacy / Terms

Ported as static Next.js pages (per design decision):
- `/privacy-policy/` → `/privacy-policy` (no redirect needed; `app/(marketing)/privacy-policy/page.tsx` exists)
- `/terms-of-use/` → `/terms-of-use` (same)

Content: copy from current WP pages verbatim.

### 7.6 Catch-all WP URL patterns

Note: external-URL destinations in Next.js `redirects()` need `basePath: false` on each entry.

- `/wp-admin/:path*` → `https://cms.hagopianink.com/wp-admin/:path*` (308, interim destination: `hagopianink.wpengine.com`)
- `/wp-login.php` → `https://cms.hagopianink.com/wp-login.php`
- `/wp-content/uploads/:path*` → `https://cms.hagopianink.com/wp-content/uploads/:path*` (308; handles externally-linked legacy image URLs)
- `/sitemap_index.xml` → `/sitemap.xml` (internal, no `basePath` flag needed)
- `/?p=:id` → `/` (best-effort; not worth resolving slug at the edge)

**Note on image URLs in WP post content:** Once WP moves to `cms.hagopianink.com`, any `<img src>` embedded in post bodies that still references the old `hagopianink.com/wp-content/uploads/...` will get a double-hop on first paint: Next.js hits the redirect rule above, browser follows to `cms.hagopianink.com/wp-content/uploads/...`. Acceptable for legacy content; new posts authored on `cms.hagopianink.com` will naturally embed `cms.hagopianink.com` URLs directly.

### 7.7 RSS feed (rewrite, not redirect)

In `next.config.ts` `rewrites()`:
- `/feed{/}?` → `https://cms.hagopianink.com/feed`
- `/feed/atom{/}?` → `https://cms.hagopianink.com/feed/atom`
- `/comments/feed{/}?` → `https://cms.hagopianink.com/comments/feed`

Rewrites preserve the URL in the address bar; subscribers see a clean `hagopianink.com/feed` even though WP renders the response.
